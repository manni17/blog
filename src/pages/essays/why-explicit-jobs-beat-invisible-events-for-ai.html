Why explicit jobs beat
invisible events for AI

A queue felt like a contract. The agent fixing the publisher could not see the consumer. A named Hangfire job is a file. The locks around that file are what keep a gift card from being charged twice or not at all.

↓ The failure the queue hid
01
The queue

RabbitMQ hid
the next file.

Steller’s pre-pivot stack used RabbitMQ between services. Built From the Rubble describes the failure in operational terms, not taste. The order service published an event. The wallet service subscribed. Those were two codebases and two context windows. When I asked the agent to fix the order flow, it could only see the part of the flow in the file it was reading. The consumer, the wallet debit, the Bamboo vendor call, and the webhook dispatch stayed invisible.

The sessions had a shape. I would describe a bug — orders completing while wallets were not debited, or debited twice. The agent loaded the order service, made a change, and reported success. The wallet service was still wrong, because the agent had never seen it. The quote I stand by: every time I asked the agent to fix an order flow bug, it changed the right service but broke two others it couldn’t see.

Message queues are asynchronous and implicit. An agent fixing a publisher has no signal that a consumer exists, or what contract it expects. Every RabbitMQ change was a gamble. Sessions opened with fifteen to twenty minutes of searching, and infrastructure — exchanges, bindings, dead-letters — filled the window before business logic did.

That is the failure mode. Not “queues are old.” The next step was not in the file, so the agent could not be responsible for it.

02
False comfort

“The queue is the contract”
was not a contract the agent could read.

The flaw card in that essay states the comfortable idea and the thing the agent actually hit. The idea: the queue is the contract, and that is enough. The hit: the dependency is hidden. A contract that lives in a broker binding is not a contract in the context window. The agent cannot grep an implicit event name and land on the consumer.

The same comfort showed up in rollback. “A saga will roll the wallet back if Bamboo fails” was the thought. The published counter is compensating work in the path the agent can open, not choreography across services. I am not drawing a saga diagram. None is published. The point the essay already makes is enough: if the compensation is implicit, the agent that edits the forward path will not update it.

Gift card orders make the miss expensive. A wallet debited twice, or an order completed without a debit, is the bug the essay names. An invisible consumer is how that bug survives a session that “succeeded.”

Names the essay lists, and does not specify. ReconciliationJob and SendWebhookJob appear beside PlaceBambooOrderJob as examples of strings an agent can search. Their bodies are not in the essays or in the AGENTS.md locks quoted here. This note does not invent them.
03
The named job

PlaceBambooOrderJob
is a file with a lock on it.

The execution week of the pivot — February 23 to March 1, $163 in the published weekly figures — is labeled “RabbitMQ out, Hangfire in.” Controllers grew fat. The golden flow collapsed into a single readable path: place order, debit wallet, call Bamboo, return PINs, fire webhook. For background work, the job is a named C# class.

PlaceBambooOrderJob is the one job whose behavior is both in that essay and in Steller’s backend AGENTS.md. The essay says an agent can grep it, open it, and read it, including the wallet rollback when Bamboo fails. The lock is tighter than the essay’s summary, and it is the rule the agent is not allowed to relax:

Lock
What the backend file requires
Retry
No retry on PlaceBambooOrderJob.
Failure
Refund on failure.
Refund errors
Swallow a refund throw.
Workers
Hangfire WorkerCount must be 2 for Bamboo. Never increase it.
Vendor calls
Always send a Bamboo Idempotency-Key.

I will not add a theory of why the worker count is 2 beyond the lock’s own phrase: it must be 2 for Bamboo, and it must not be increased. Raising it would look like a performance fix. The file says it is not available as a fix. I will also not paste a job catalog. One job is specified. The others are names.

Public partner behavior lines up with the refund lock only at the level both texts actually state. developers.steler.org says the wallet is debited when the order is created and refunded on failure. The AGENTS.md lock says this job does not retry and does refund on failure. I am not asserting a line-by-line identity between those two sentences. They are the published partner fact and the published operator rule.

04
Debug

A name changes
what “done” can mean.

Debugging an explicit job is a search. Open the controller. Find the enqueue of PlaceBambooOrderJob. Read the rollback in that job. The scorecard’s line for the old system is “trace a message through three or more services. Often a guess.” The new line is “read the controller top to bottom. The cause is visible.”

The Idempotency-Key lock changes the vendor call the same way. A retried or repeated Bamboo request without a key is how a gift card provider can mint a second order the partner did not ask for twice. The partner-facing idempotency field is a different published mechanism — referenceId on the Steller API — and the next essays keep them separate. What belongs here is the operator rule: vendor calls always send the key. An agent that removes it to “simplify the client” has violated AGENTS.md.

No-retry is the same kind of rule. A job that throws, retries, and places a second vendor order is the failure mode a gift card API cannot shrug off. The lock pairs no-retry with refund-on-failure, and it says to swallow a refund throw so a failed refund does not become another vendor attempt. That last clause is easy to “clean up.” Cleaning it up is the forbidden move.

Smoke for this path, after config changes, is also explicit. Health gate first. Then POST /api/orders returns 202. Then poll until Completed. HTTP 200 alone is not the business outcome. The order’s terminal state is.

05
If events return

Events can return
only as something an agent can see.

The limits chapter does not ban every future message. It bans the invisible kind. If Steller grows past one golden flow, the published alternative is domain-bounded services with explicit, synchronous interfaces — not event-driven, and not invisible. Independent scaling is a real exit from fat controllers: the essay’s example is a Bamboo integration that needs many times the resources of catalog sync. Even then, the interface the agent crosses has to be readable. A broker binding is not that interface.

I am not scheduling that return. Steller’s published system has one golden flow, not forty, and it has not announced that the Bamboo path must scale apart from the rest. A job catalog, a retry matrix, and a saga diagram are unpublished. Leaving them out is the point of writing this from the record.

The rule that survives either shape is the second principle in the rubble essay. Name everything so it can be grepped. If you cannot search it, the agent cannot see it. Implicit pub/sub is context poison. An explicit job is a file, a lock, and a smoke that ends in Completed or in a refund — not in a consumer nobody opened.
