The failure-first
onboarding

The old path spent its time on setup gaps that looked like API bugs. The published fix is to surface three failures immediately, and to measure the moment the system proves itself.

↓ Setup gap, not a mystery defect
01
Setup gaps

Most of the old pain
was not an API bug.

We Stopped Teaching. We Started Doing. describes the old Steller onboarding as PLG 1.0 by default. A partner signed up, reached a dashboard, and faced documentation. They had to read the API reference, understand the wallet, find a working SKU, construct a valid request, and run it. For a developer that took hours. For a business user it took days, or they churned. The path included debugging the 400, 401, or 422 they hit, then polling for status if they remembered to.

The essay’s claim about those failures is specific, and this note does not add a rate to it. When integration failures in the old flow were looked at, almost none of them were API bugs. The system was working. The partner had made an error documentation did not prevent, because they had not read it, had not retained it, or had guessed. No percentage is published. “Almost none” is the phrase. I will not turn it into a dashboard.

That is the difference between a setup gap and a defect. An invalid key, an empty catalog, and an unfunded wallet are states of the account. A partner who treats them as product bugs loses the hour the PLG essay describes. Failure-first onboarding means those states are the start of the path, not a surprise after a carefully built payload.

The developer hub still has a place. developers.steler.org publishes getting started, an error reference, rate limits, and a glossary. Failure-first does not delete the reference. It refuses to make the reference the first thing a partner must survive.

02
Three failures

The same three failures,
two published surfaces.

Both essays name three early failures: an invalid API key, an unfunded wallet, and an empty catalog. The wording is not identical, and I will not collapse it into one screen I have not published as a single spec.

The 20–40 minute figure belongs only to the invalid-key row of the PLG essay. The Complete Story does not repeat that range. It says the cryptic version takes hours. Both are published. Neither is a study with a sample size I can cite, because none is printed.

The hub adds facts that sit beside these failures without replacing them. Partner calls authenticate with an x-api-key header. The dashboard password is not the API key. Keys are not shared across environments. Staging and production use a separate base URL and a separate key. Staging uses a sandbox vendor and test funds, on real API flows. Go-live asks for a successful staging end-to-end run before production credentials. An invalid key and a key from the wrong environment are the sort of setup gap those rules exist to make legible. I am not publishing a new error string beyond the two essays.

03
Two orders

There is not one
canonical step list.

The two essays do not tell the 60-second path in the same order. Citing one and calling it the product would hide the other.

PLG
Wallet, catalog, order, track
Confirm the wallet, with balance shown and no setup. Fetch the catalog, with ready-to-order SKUs already filtered. Create the order from a pre-constructed request. Track the lifecycle, with 202 Accepted and live polling. The essay’s path card titles the same four moments: wallet confirmed, catalog loaded, first order placed, status trackable.
Story
Auth, wallet, order, track
The Complete Story starts with auth: credentials in, a JWT back, no configuration. Then a color-coded wallet. Then a pre-constructed order that locks the wallet row, queues the work, and returns HTTP 202 with a tracking ID. Then a poll about every three seconds until codes decrypt and display.

The hub’s example calls are a third published sequence, and they are examples, not a claim that they replace either essay: GET /api/wallet/me, GET /api/partner/catalog/orderable, POST /api/orders, GET /api/orders/{id}. Auth on those calls is the API key header. The Complete Story’s first step is a JWT from credentials. This essay does not invent a diagram that merges the JWT and the API key into one handshake. They are two published descriptions. The hub does say the dashboard password and the API key are different secrets.

What both essays agree on is the time box and the role. Under sixty seconds to a first successful API transaction. The partner reviews a result the system already assembled. Zero documents required to start. The PLG essay’s old path was hours or days. That contrast is the onboarding claim. It is not a single ordered checklist I can pretend is unique.

04
Diagnosis

Diagnosis is the path.
The happy path is not the whole product.

The PLG essay’s line is the definition this note uses. Great onboarding is fast diagnosis, not just happy paths. Surface failures immediately. Remove ambiguity. Make the right move obvious. The Complete Story says the same thing in its own words: three failures surface immediately, with a next step instead of a cryptic error. Fast diagnosis is part of the path, not only the happy path.

PLG 1.0, in that essay, asked how to reduce friction. PLG 2.0 asks how to eliminate the work. The partner stops being the builder of the first request and becomes the reviewer of a result. Wallet balance is visible before the order. The catalog is filtered to what can be ordered. The payload is pre-constructed. The first response worth trusting is 202 Accepted, which the next note treats as its own decision. The PIN is not the first proof.

The hub’s error reference, and its rate limits, sit beside that stance. One hundred requests per minute per API key, and ten requests per second on orders. A 429 may be plain text. Use Retry-After, and retry an order with the same referenceId. Those are tools for a partner who has already seen the system work. They are not the first minute. Optional IP allowlisting is a hub security note, not a step the 60-second path requires.

05
Moments

Measure the moment
of proof, not the checklist.

The PLG essay rejects feature-adoption metrics — did they open the catalog, click the order button, finish a setup checklist — because a finished checklist with no order is not value. It publishes four moment metrics instead. TTV-Auth is time from signup to confirmed authentication. TTV-Order is time from auth to the first 202. TTV-Track is time from the first order to the first visible status poll. TTV-Scale is time from the first order to the first production volume. The first three sit in the getting-started flow. The fourth is the conversion from testing to production.

The Complete Story scores the path on four time-to-value metrics with the shorter labels Auth, Order, Track, and Scale. I am not merging the definitions further than that overlap. The PLG labels are the ones with the “time from … to …” sentences.

TTV-Order

Failure-first onboarding is how those moments stay short. A partner who spends twenty to forty minutes on a 401 never reaches TTV-Order. A partner who sees an empty catalog named, or a zero balance before they post, does not burn the minute on a request that cannot succeed. The confidence the essays are after is the internal conviction that the thing works. That conviction is a partnership problem. It is also a product problem, and it starts by showing the failure before asking for the order.

No unpublished failure-rate analytics belong at the end of this note. The evidence is the two essays, the hub’s auth and environment rules, and the 60-second claim. The work the partner used to do first is the work the product now does, or the work it refuses to hide.
